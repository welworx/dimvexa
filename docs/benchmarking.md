# Benchmarking against other libraries

Dimvexa's claim is "exact, fast and loud about what it cannot do". This page says how that is
measured against other unit libraries, so that anybody can reproduce and challenge the numbers.
Own-performance numbers (the M0 spike) are in [`docs/benchmarks/M0.md`](benchmarks/M0.md).

## Rules

1. **No claim without a dated run.** The README, the docs and release notes may say "fastest",
   "most accurate" or similar only with a link to a dated benchmark run (workflow run or committed
   result files) that shows it, for the row concerned. Until then no such claim is made.
2. **Never invent or edit numbers.** Result files are produced by the runners and published as
   they are. The report is generated from them by `benchmarks/tools/report.py`.
3. **Best idiomatic use for every library.** Each runner measures a library's plain API and its
   fastest documented way (prepared converters, factor extraction, typed units, array APIs). Raw
   loops and NumPy/`memcpy` are shown as ceilings, never as competitors.
4. **No cherry-picking.** Every corpus case, every conversion and every batch size is reported,
   including those where Dimvexa loses or fails.
5. **Maintainers may review their runner.** Open a *Benchmark runner review* issue; corrections
   are applied before publication.

## What is measured

| # | Measurement | Notes |
|---|---|---|
| 1 | Prepare cost | Parsing and building a conversion, cold (fresh registry or process state) and warm |
| 2 | Scalar conversion | A prepared conversion applied to one value; the loop overhead of the host language is measured and shown next to it |
| 3 | One-shot | Parse a string such as `10 m/s` and convert it |
| 4 | Batch | 10^3, 10^5 and 10^6 values, reported as ns per element; identical inputs in every language (LCG32 stream, `corpus/perf.json`) |
| 5 | Startup and size | Import time over an empty interpreter, peak RSS, installed package size (Rust: registry build time, runner binary size) |
| 6 | Accuracy | Every must-convert case against the exact rational truth: max and median error in ulp, count above the tolerance (4 ulp), count above 1 ulp |
| 7 | Coverage and safety | Every case classified as correct, wrong value, unsupported error, or (for ambiguous or invalid requests) refused versus **silently accepted** |
| 8 | Dimvexa itself | The same checks, including the cases where it fails. Dimvexa is run through its Rust API (fast and exact paths) and the CLI; Python and WASM entries are stubs until those bindings exist |

Conversions timed: `m/s` to `km/h` (linear), `psi` to `kPa` (linear), `degC` to `degF` (affine),
`kJ/(kg.K)` to `Btu_IT/(lb.delta_degF)` (compound).

## The corpus

`benchmarks/corpus/*.json`, generated by `python3 benchmarks/tools/gen_corpus.py` (standard
library only, offline, deterministic; `--check` verifies the committed files).

* `must_convert.json`: the exact rational result, its `f64` rounding and a cited source for every
  case. Cases come from Dimvexa's golden vectors and from hand-written categories (SI,
  imperial/US, pressure, process engineering, temperature points and differences, compound
  units). The truth is computed by an **independent oracle** (`corpus-src/truth.toml` with
  `Fraction` arithmetic), not by Dimvexa. Where the oracle can evaluate a Dimvexa vector the two
  must agree or generation fails (63 vectors checked).
* `must_refuse.json`: requests that must be refused or flagged: ambiguous names (`ton`, `gal`,
  `oz`, `pt`, `cal`, `Btu`, `hp`, `mile`, `foot`, bare `ppm`), missing context (`Nm3` to `m3`,
  gauge to absolute pressure, mass fraction to mole fraction, water head), temperature kind
  errors (adding two absolute temperatures) and plain dimension mismatches. Any error counts as
  a refusal; the reason is compared only for Dimvexa.
* `coverage.json`: unit lists by category plus Dimvexa's own table.
* A documented default (pint reading `ton` as the short ton) still counts as silently accepted,
  because the request did not say which ton.

Unit spellings differ per library; `benchmarks/translations/<lib>.json` maps Dimvexa's explicit
names to each library's. Only explicit names are mapped, never ambiguous bare names. Every
case record stores the string actually used, so a wrong mapping is visible and can be fixed.

## Statistical rules

* Warm-up, then many samples (15; 5 for the largest batch); each sample times a loop sized to
  last at least 50 ms (batches: one call per sample).
* Report the **median and the median absolute deviation** with the raw samples; never a single mean.
* One job, one machine, one run for all libraries. Record OS, CPU model, core count and CPU governor
  (cloud runners do not allow pinning it; note it when it cannot be set).
* Pin versions: `requirements.lock.txt` with hashes, `package-lock.json`, `Cargo.lock`. A run
  without lockfiles is labelled `unlocked` in the result and the report.
* GitHub-hosted runners are noisy and share hardware. Treat Python and JavaScript wall-clock results
  as indicative. For Rust, prefer instruction counts (the iai-callgrind suite in `extras/`) when a
  claim depends on a small difference.
* Dimvexa fast-path accuracy is 1 ulp (linear) and 2 ulp (affine) by contract
  ([`precision.md`](precision.md)); the 4 ulp "wrong" tolerance here is deliberately loose so that a
  library is only called wrong when it is clearly off.

## Running it

```console
python3 benchmarks/tools/gen_corpus.py --check       # corpus is current
python3 -I benchmarks/tools/test_report.py           # tests of the corpus and the report generator
cd benchmarks/runners/dimvexa-rs && cargo run --release -- --cli ../../../target/release/dimvexa
python3 benchmarks/python/run_pint.py                # needs: pip install -r benchmarks/python/requirements.in
node benchmarks/node/run_mathjs.js                   # needs: npm install in benchmarks/node
python3 benchmarks/tools/report.py                   # results/*.json -> docs/benchmarks/comparison.md
```

`--quick` runs a few samples as a smoke test; never publish quick results. The workflow
`.github/workflows/bench-compare.yml` (manual and weekly, never required, not part of
`ci-success`) runs everything in one job and uploads `benchmarks/results/` as an artifact. Result
schema: `dimvexa.bench.result/1`, one file per library and version, with `library`, `runtime`,
`machine`, `date_utc`, `lockfile`, `corpus_id`, `parameters`, `modes`, `performance` (per mode and
conversion: `prepare_cold`, `prepare_warm`, `scalar`, `loop_overhead`, `oneshot`, `batch`; each a
median, MAD, min, max and raw samples), `startup` and `semantics` (per semantic mode: counts,
accuracy summary, per-case records, coverage). `lock.sh` in `benchmarks/tools/` creates the lockfiles
on a networked machine.

## Status of the runners

Written on a machine that could reach none of the package registries, so no competitor library was
ever installed. Only Dimvexa and the ceilings were run, and only as smoke tests.

| Runner | Runner written | Verified offline | Run on a networked machine |
|---|---|---|---|
| Corpus generator | yes | yes (reproducible, 63 vectors cross-checked) | not needed |
| Report generator | yes | yes, on fixture data only | no |
| Dimvexa, Rust API (`benchmarks/runners/dimvexa-rs`) | yes | built and smoke-run (`--quick`) | no full run yet |
| Dimvexa CLI (spawn per conversion) | yes | smoke-run | no full run yet |
| Rust ceilings (plain loop, memcpy) | yes | smoke-run | no |
| Python ceilings (pure Python, NumPy) | yes | smoke-run | no |
| JavaScript ceiling (raw loop) | yes | smoke-run | no |
| uom | yes | **no: never compiled**, unit names unchecked | no |
| ucum-units | **not written** (crate and API not verified) | no | no |
| pint, unyt, astropy.units | yes | syntax only; library calls unchecked | no |
| mathjs, js-quantities, convert-units | yes | syntax only; library calls unchecked | no |
| Dimvexa Python and WASM bindings | stub (bindings do not exist) | no | no |
| `bench-compare.yml` | yes | YAML parse only; `actionlint` not available; two action SHAs are placeholders | no |

The `translations/*.json` files and the `lockfile` policy are likewise unverified. Expect small
fixes on the first run; fix the runner, never the numbers. Smoke runs showed, among other things,
that the M0 unit table has no `cP`, `cSt`, `psig`, `Nm3`, `scf` or `bbl` yet; those cases are
reported as unsupported for Dimvexa until the process pack exists.
