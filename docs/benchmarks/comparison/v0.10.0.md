# Comparison with other unit libraries: Dimvexa 0.10.0

Hand-written summary of one full `benchmarks/run_all.sh` run (2026-11-15). Every number below is
copied from [`comparison.md`](comparison.md) (generated) and the raw files in
[`benchmarks/results/`](../../../benchmarks/results/). Method and rules:
[`../../benchmarking.md`](../../benchmarking.md). The previous release comparison is
[`v0.5.0.md`](v0.5.0.md); its tables are **not** comparable with these ones (different corpus,
different day, different unit table).

## What was run

* Dimvexa 0.10.0 built from commit `58f319a` (the head of `main` when the run was made, version
  0.10.0 in `Cargo.toml`; there is no `v0.10.0` tag yet). The result files are labelled
  `0.10.0+58f319a-dirty`, and that is accurate: the run started with two uncommitted changes that
  the run needs and that were committed afterwards in `203696e`: the regenerated corpus
  (`gen_corpus.py`; the committed one was stale after the US customary units) and the
  `benchmarks/runners/dimvexa-rs/Cargo.lock` version lines (`0.5.0` to `0.10.0`). Neither touches
  library code (`crates/`, `bindings/`). Rule 5 of `benchmarking.md` asks for a clean checkout of the
  release commit; this run does not strictly meet it, so repeat it on the tagged commit when the
  release is cut.
* One shared cloud VM: Intel Xeon 2.10 GHz, 4 cores, Linux 6.18, CPU governor not readable. rustc
  1.99.1, CPython 3.13.18, Node 22.23.4. Runners ran one after another.
* Competitor versions are exactly those in the lockfiles, verified by
  `benchmarks/tools/check_versions.py` before the run and again on the result files: pint 0.26.2,
  astropy 8.0.2, unyt 3.2.0, mathjs 13.2.0, js-quantities 1.8.0, convert-units 2.3.4, uom 0.36.0.
* Corpus `69bf1471279e6d39`: 302 must-convert and 30 must-refuse cases (40 must-convert cases are
  independent, from published sources). Two Dimvexa golden vectors with irrational expected values
  are not cases; they are counted in the manifest.
* One run, not repeated. The machine is noisy: a difference is only called a difference where it is
  larger than the spread (MAD) of both sides.

| convert-units | 83 | 219 | 27 | 4.4e18 ulp |

For pint, unyt, convert-units and uom the 4.4e18 ulp is a case whose exact result is 0 where the
library returns a tiny non-zero number (for example 5.7e-14 from pint on `dv-common-034`).

Dimvexa's four unsupported cases are refusals by design, not missing units: `hw-043` (`psig`, a
gauge pressure needs the ambient pressure), `hw-056` and `hw-057` (`Nm3`) and `hw-058` (`scf`), both
gas volumes at a reference state. The error says why in each case. By origin of the case Dimvexa
answers 179/179 golden vectors, 79/83 hand-written cases and 40/40 independent cases correctly;
the four missing ones are the hand-written ones above. Its 1 ulp results (for example
`dv-common-036`, 273.15 K as 273.15000000000003 on the fast path and the exact-to-f64 path) are within
the documented bound (`docs/precision.md`).

## Safety (30 must-refuse cases)

| Library | Ambiguous names (10): refused / accepted with a default | Other invalid requests (20): silently accepted |
|---|---|---|
| dimvexa 0.10.0 (all modes) | 10 / 0 | 0 (3 not applicable) |
| pint | 0 / 10 | 2 |
| mathjs | 3 / 7 | 5 |
| unyt | 4 / 6 | 4 |
| astropy | 4 / 6 | 4 |
| js-quantities | 1 / 9 | 3 |
| convert-units | 8 / 2 | 0 (3 not applicable) |
| uom | 0 / 0 (10 not applicable) | 0 (20 not applicable) |

An "accepted with a default" ambiguous name is a documented policy choice (for example pint reading
`ton` as the short ton), reported apart from a missing check.

Dimvexa refused all 27 applicable requests, but only 25 for the intended reason. Two were refused
with `parse_error` instead of the intended code: `ref-015` (`wt%` is not parsed) and `ref-020`
(`mH2O` is not a known unit symbol, so the water-head request fails at parsing). They are refused,
not accepted; the reason is wrong, which is a finding against the runner's expectation or the error
design, not a silent wrong answer.

## Speed (prepared conversion, median ns per conversion, MAD in brackets)

Scalar means one prepared conversion applied to one value including the loop; batch is ns per element
for 1,000,000 values. Ceilings (a plain Rust loop, `memcpy`, NumPy) do no unit handling and are in
`comparison.md`. Only the fastest competitor of each kind (in its fastest mode) is shown; every
library is in the generated tables.

| Conversion | Dimvexa scalar | Best other scalar | Dimvexa batch 1M | Best other batch 1M |
|---|---|---|---|---|
| m/s to km/h | 0.624 (0.018) | uom 0.39 (0.024) | 0.609 (0.006) | uom 0.582 (0.017) |
| psi to kPa | 0.68 (0.048) | uom 1.25 (0.004) | 0.705 (0.047) | unyt (factor) 0.645 (0.018) |
| degC to degF | 0.63 (0.005) | uom 0.635 (0.076) | 0.685 (0.018) | uom 0.61 (0.025) |
| kJ/(kg.K) to Btu/(lb.delta_degF) | 0.705 (0.033) | mathjs (factor) 7.96 (0.363) | 0.653 (0.009) | astropy (unit_to) 0.69 (0.007) |

How to read it:

* **Faster, larger than the spread:** psi to kPa scalar (0.68 against uom 1.25); the compound scalar
  (0.705 against mathjs 7.96; uom cannot express it); the compound batch (0.653 against astropy 0.69,
  a small gap of 0.04 ns that is still above both spreads).
* **Not called a difference:** degC to degF scalar (0.63 against uom 0.635, whose MAD is 0.076);
  psi to kPa batch against uom (0.661 (0.013)); compound batch against pint (0.67 (0.024)).
* **Slower:** m/s to km/h scalar (uom 0.39 against Dimvexa 0.624); m/s to km/h batch (uom 0.582 against
  0.609; the gap is 0.027 ns, only just above uom's MAD); degC to degF batch (uom 0.61 against 0.685);
  psi to kPa batch against unyt's factor mode (0.645 against 0.705, a gap of 0.06 ns that is just
  above Dimvexa's MAD of 0.047). The batch rows of all of these sit at the memory-bound ceiling
  (the Rust `plain_loop` is 0.60 to 0.70 ns), so batch speed is not a differentiator in this run.
* Dimvexa's exact path (rational arithmetic, no `f64` factor) costs 21 to 50 ns per scalar
  conversion and 40 to 63 ns per element in a batch.
* One-shot (parse a string like `10 m/s`, build, convert): Dimvexa 0.98 to 1.92 us for the three
  simple conversions and 3.84 us for the compound one, against 3.18 to 6.55 us for the fastest
  competitor (mathjs in three rows, js-quantities `swift` for degC to degF at 5.44 us).
* Bindings, scalar: the Python `conv` mode 83 to 95 ns and the WASM `conv` mode 7.5 to 9.7 ns per
  conversion; the plain-API modes cost 1.3 to 5.3 us (Python) and 2.2 to 7.5 us (WASM).

Python and JavaScript wall-clock figures on this VM are indicative only.

## What this does and does not support

* Supported by this run: on this corpus Dimvexa answered every must-convert case it did not refuse
  by design within 1 ulp, with no wrong value, and refused every ambiguous name and every other
  applicable invalid request; the other libraries did not on the same cases.
* Not supported: "fastest". Dimvexa's prepared conversions are at or near the best of the compared
  libraries, but uom is faster in several rows, and several rows are inside the noise.
* Not run: criterion and iai suites (`extras/`), any machine other than this VM, any repetition of
  the run, the Excel add-in, a run on a clean tagged checkout.
* The corpus was chosen by this project (40 of the 302 cases come from independent published
  sources). A different corpus can give different counts. The pint `ton` style defaults are reported
  as policy, not as errors.
