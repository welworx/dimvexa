# Comparison with other unit libraries: Dimvexa 0.11.0

Hand-written summary of one full `benchmarks/run_all.sh` run (2026-11-18). Every number below is
copied from [`comparison.md`](comparison.md) (generated) and the raw files in
[`benchmarks/results/`](../../../benchmarks/results/). Method and rules:
[`../../benchmarking.md`](../../benchmarking.md). Earlier dated runs: [`history/`](history/).

## What was run

* Dimvexa built from commit `0578bd9`, a clean checkout. Its library code (`crates/`, `bindings/`,
  Cargo files) is identical to the 0.11.0 release-preparation commit `3c9a955` and to the branch
  head at the time of writing; only benchmark tooling and docs differ (the harness was made
  portable to macOS in `0578bd9`).
* **One Apple Mac, not the shared Linux VM of earlier comparisons:** Apple M2, 8 cores, 16 GiB,
  macOS 26.5.1 (Darwin 25.5.0), CPU governor not readable. rustc 1.99.1, CPython 3.13.18,
  **Node 20.19.3** (earlier runs used 22.23.4). Runners ran one after another.
* Competitor versions are exactly those in the lockfiles, verified by
  `benchmarks/tools/check_versions.py` before the run and again on the result files: pint 0.26.2,
  astropy 8.0.2, unyt 3.2.0, mathjs 13.2.0, js-quantities 1.8.0, convert-units 2.3.4, uom 0.36.0.
* Corpus `69bf1471279e6d39`: 302 must-convert and 30 must-refuse cases (the corpus of the 0.5.0
  comparison had 245 and 30, so counts are **not comparable** with it). Two Dimvexa golden vectors
  with irrational expected values are not cases, because the corpus holds exact rationals only.
* One run, not repeated. A difference is only called a difference where it is larger than the
  spread (MAD) of both sides.
* Not comparable with `v0.5.0.md`: another machine, another Node and another corpus. No row in this
  file is compared with a number from that run.

| Library / mode | Answered | Unsupported | Wrong (more than 4 ulp) | Worst error |
|---|---|---|---|---|
| dimvexa 0.11.0 Rust, exact path | 298 | 4 | 0 | 1 ulp |
| dimvexa 0.11.0 Rust, fast path | 298 | 4 | 0 | 1 ulp |
| dimvexa 0.11.0 Rust, text (exact decimal) | 298 | 4 | 0 | 0 ulp |
| dimvexa-py, dimvexa-wasm | 298 | 4 | 0 | 1 ulp |
| pint | 231 | 71 | 10 | 4.4e18 ulp |
| astropy | 182 | 120 | 28 | 1.2e8 ulp |
| mathjs | 171 | 131 | 22 | 1.8e15 ulp |
| js-quantities | 169 | 133 | 37 | 3.5e9 ulp |
| unyt | 160 | 142 | 24 | 4.4e18 ulp |
| convert-units | 83 | 219 | 27 | 4.4e18 ulp |
| uom | 33 | 269 | 15 | 4.4e18 ulp |

**The four cases Dimvexa does not answer are refusals by design**, not errors: `psig` to `barg`
(a gauge pressure is measured from an ambient pressure that varies with altitude and weather),
`Nm3/h` to `Nm3/min` and to `Nm3/s`, and `scf/min` to `scf/h` (gas volumes at reference conditions
that Dimvexa does not relate). They are the category `process` of the corpus and counted as
unsupported. Every other case is answered within 1 ulp, with no wrong value.

For pint, unyt, convert-units and uom the 4.4e18 ulp is a case whose exact result is 0 where the
library returns a tiny non-zero number (for example 5.7e-14 from pint on `dv-common-034`).

## Speed (prepared conversion, median ns per conversion, MAD in brackets)

Scalar means one prepared conversion applied to one value including the loop; batch is ns per
element for 1,000,000 values. "Dimvexa" is the Rust API, prepared conversion on the fast path.
Ceilings (a plain Rust or NumPy loop) do no unit handling and are in `comparison.md`. Only the
fastest competitor of each kind is shown; every library is in the generated tables.

| Conversion | Dimvexa scalar | Best other scalar | Dimvexa batch 1M | Best other batch 1M |
|---|---|---|---|---|
| m/s to km/h | 0.393 (0.005) | uom 0.570 (0.155) | 0.173 (0.004) | astropy 0.157 (0.0003), uom 0.157 (0.0006) |
| psi to kPa | 0.393 (0.003) | uom 0.965 (0.231) | 0.174 (0.003) | unyt 0.161 (0.0015) |
| degC to degF | 0.411 (0.002) | uom 0.458 (0.001) | 0.168 (0.0005) | uom 0.164 (0.0008) |
| kJ/(kg.K) to Btu/(lb.delta_degF) | 0.384 (0.0005) | mathjs 5.21 (0.016) | 0.157 (0.0001) | unyt 0.158 (0.0013) |

How to read it:

* **Faster, larger than the spread:** psi to kPa scalar (Dimvexa 0.393 against uom 0.965); degC to
  degF scalar (0.411 against uom 0.458, both with a very small spread); the compound scalar (0.384
  against mathjs 5.21; uom cannot express it).
* **Not called a difference:** m/s to km/h scalar (uom 0.570 has a MAD of 0.155, the gap is about
  one MAD); the compound batch (0.157 against unyt 0.158, inside unyt's MAD of 0.0013).
* **Slower:** the batch of 1,000,000 for m/s to km/h (0.173 against 0.157), psi to kPa (0.174
  against unyt 0.161) and degC to degF (0.168 against uom 0.164): each is a few percent above the
  best competitor, by more than the spread of both sides. All of these batch rows sit next to the
  memory-bound ceiling (Rust plain loop 0.157 ns, `memcpy` 0.179 ns on the degC row), so batch speed
  does not separate the libraries in this run.
* Dimvexa's exact path (rational arithmetic, no `f64` factor) costs 10 to 33 ns per scalar
  conversion and 25 to 43 ns per element in a batch.
* One-shot (parse a string like `10 m/s`, build, convert): Dimvexa 0.84 to 3.4 us on the prepared
  path (0.84 degC to degF, 0.93 psi to kPa, 1.7 m/s to km/h, 3.4 compound), against 1.9 to 4.5 us
  for the fastest competitor of each (mathjs 1.93, 2.92 and 4.45; js-quantities 3.57 for degC to
  degF). The CLI spends 2.2 to 2.3 ms per call, which is process start.
* Bindings: the Python binding applies a prepared conversion in 82 to 85 ns per call (the Python
  loop costs 21 ns of that) and 0.22 to 0.23 ns per element in a NumPy batch; the WebAssembly
  binding takes 5 to 8 ns per call and 0.5 to 0.9 ns per element in its batch and in-place modes
  (about 6 ns per element when called one value at a time).

Python and JavaScript wall-clock figures on a laptop are indicative only.

## What this does and does not support

* Supported by this run: on this corpus Dimvexa answered every case it supports within 1 ulp, with
  no wrong value, refused every ambiguous name and silently accepted no invalid request; the other
  libraries did not on the same cases.
* Not supported: "fastest". Dimvexa's prepared conversions are at or near the best of the compared
  libraries, but not in every row (the three batch rows above), and some rows are inside the noise.
* Dimvexa answers 298 of 302 cases; the four it refuses (gauge pressure and gas volumes at reference
  conditions) count as unsupported in the table above, so its answered count is lower than a
  library that returns a number for them.
* Not run: criterion and iai suites (`extras/`), any machine other than this Mac, any repetition of
  the run, the Excel add-in, a Linux run of this release.
* The corpus has 302 cases that were chosen by this project (40 from independent published
  sources). A different corpus can give different counts. The pint `ton` style defaults are
  reported as policy, not as errors.
