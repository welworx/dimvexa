# M0 benchmarks

Measured, not estimated. Reproduce with `cargo bench -p dimvexa --bench m0`. The raw table lives in the output of that command; the numbers quoted here come from the run made on 2026-11-07 (re-run after `apply_exact_f64` was added; the fast-path code itself was not changed in that step, the two new rows are the only addition).

## Machine and method

- Intel Xeon (model string hidden by the hypervisor), 2 vCPU, 8 GB RAM, Linux 6.18, a shared cloud VM. Expect noise; min and max are in the raw output.
- rustc 1.97.0, release profile (thin LTO, codegen-units = 1), default target CPU (x86-64 baseline, SSE2).
- The criterion and iai-callgrind suites could not be built here (the crates registry was blocked by network policy), so the harness is a std-only one: 15 samples per row, median reported, `black_box` on inputs and outputs. The criterion and iai files are written in `extras/` but have NOT been run.
- Single thread. No caching, no parallelism, no GPU (correctness first in M0).

## Plan targets

| Target | Result | Verdict |
|---|---|---|
| Under 5 ns per prepared scalar conversion | 0.52 ns throughput (linear), 0.54 ns (affine); latency-bound chain 2.8 ns (linear), 4.1 ns (affine); 0.55 ns for a single opaque call | Met, including the pessimistic dependent chain |
| Slice conversion within a small multiple of a plain multiply loop | 10^6 elements: 0.557 ns/elem vs 0.537 for the plain loop (ratio 1.04), memcpy ceiling 0.544 (ratio 1.02). Same ratio at 10^3 and 10^5 | Met (equal to the plain loop within noise) |
| Fast path within 1 ulp of the exact path | Linear: max 1 ulp. Affine: max 2 ulp, in about 0.3 percent of cases (2,073 of 704,140 in the large affine set) | Linear met at 1 ulp. Not run: 10^8-element slices and thread scaling.

## Vectorisation check (assembly, as seen)

`crates/dimvexa-testkit/examples/asm_probe.rs` wraps `apply_slice` and `apply_in_place` in non-inlined functions; the release binary was disassembled with `objdump -d`.

- Default target: both functions contain `mulpd` and `addpd` (packed double, 128-bit SSE2) alongside scalar `mulsd`/`addsd` for the loop tail. They are vectorised.
- `-C target-cpu=native`: `vmulpd` and `vaddpd` on `ymm` registers (256-bit AVX), plus scalar tails.
- Not inspected: aarch64, and whether the compiler unrolls identically on other rustc versions.

## Findings worth keeping

- Large slices are memory-bound: at 10^6 elements the loop runs at memcpy speed, so no hand-written SIMD is justified.
- `apply_in_place` looks slower than `apply_slice` only because the row includes cloning the input.
- An O(n) suggestion scan made an unknown-symbol lookup cost 171 us at 10,000 units; a lowercase index brought it to about 0.3 us.
- Binary (Stein) gcd on `u128` was tried and measured slower than Euclid (about 115 vs 85 ns for `Ratio::checked_mul`), so it was reverted (plan section 6.2 gate).
- Parsing and building a conversion costs microseconds, which is why the API prepares once and applies many times. Exact-path calls cost 50 ns (rational in, rational out) to about 300 ns (`apply_exact_f64`: `f64` in and out, correctly rounded) and are for audit, not bulk work; the fast path is roughly 500 times cheaper per value.

## Accuracy of the fast path (decision recorded)

The M0 measurement showed that the affine fast path can be 2 ulp away from the correctly
rounded exact result, in about 0.3 percent of cases, while the linear path never exceeds
1 ulp. The owner accepted this (ADR-002): **linear at most 1 ulp, affine at most 2 ulp**, for
finite inputs with a normal, non-overflowing result. Nothing was changed in the fast path; the
guarantee is now documented in `docs/precision.md` and on every public conversion method, and
`crates/dimvexa-testkit/tests/differential.rs` fails the build when a result exceeds it.

Latest counts (release build; 378 same-dimension pairs of the seed table and the large
temperature set; ulp distance from the correctly rounded exact result):

| Set | Compared | 0 ulp | 1 ulp | 2 ulp | 3+ ulp |
|---|---:|---:|---:|---:|---:|
| Linear, seed table | 226,931 | 178,930 | 48,001 | 0 | 0 |
| Affine, seed table | 5,197 | 3,771 | 1,412 | 14 | 0 |
| Affine, large set (8 temperature pairs, with 30,000 inputs near each zero point) | 704,140 | 516,108 | 185,959 | 2,073 | 0 |

A one-off search over 144 million affine inputs (not part of the test suite) also found a
maximum of 2 ulp.

## Regression guard

`cargo xtask bench-check` runs the m0 bench and compares the guarded rows (scalar apply, `apply_slice`, `apply_in_place`, `apply_exact_f64`) with `docs/benchmarks/baseline-m0.tsv`, the median of three runs recorded on 2026-11-08 (4 vCPU shared VM, rustc 1.97.0, bench profile) before any exact-path change. A row is slow if it is more than 10 percent and more than 0.03 ns above the baseline; if any row is slow the bench is rerun (3 runs in total by default) and each row is judged by its best median, so a noisy neighbour does not fail the check but a slowdown that survives three runs does. The baseline is only comparable on the machine that recorded it; re-record with `--update` on a new machine or toolchain. `--input FILE` checks a saved bench output.

## Exact path speed-up (2026-11-08)

Where the time went in `apply_exact_f64` (linear, ~320 ns before): `Ratio::to_f64` alone cost
~222 ns (one quotient bit per loop turn with `i128` shifts and compares), the four gcd
reductions (`from_f64`, `checked_mul`, `checked_add`, `new`) cost the rest; the `apply_exact`
rational step itself is ~60 ns. Chunked quotient bits in `to_f64` took the linear row from ~320
to ~155 ns; computing from an unreduced fraction (every step checked, overflow falls back to the
reduced path) took it to ~39 ns. Results are bit-identical (`differential`, `exact_f64`, and a
randomised old-vs-new test in `conversion.rs`).

Serious run: 20 interleaved old (263659d) / new (93c47e6) runs of the same `m0` binaries, same
VM, 4 vCPU shared, rustc 1.97.0, bench profile; median of the 20 per-run medians, min, and MAD
(ns/op). One of the 20 pairs overlapped a `bench-check` run; medians absorb it.

| row | old median (min, MAD) | new median (min, MAD) |
|---|---:|---:|
| apply_exact_f64, linear | 317.5 (300.9, 7.5) | 39.4 (37.8, 1.1) |
| apply_exact_f64, affine | 363.3 (351.2, 5.4) | 48.7 (46.5, 1.1) |
| Ratio::to_f64 | 222.2 (215.6, 4.8) | 34.1 (32.7, 0.5) |
| Ratio::checked_mul | 98.7 (96.7, 1.3) | 50.8 (48.3, 0.8) |
| apply_exact (rational, linear) | 60.6 (58.1, 1.5) | 57.0 (54.7, 1.1) |
| Ratio::checked_add | 108.2 (105.7, 1.2) | 109.2 (106.0, 1.9) |
| conversion("degF","degC") | 1210.8 (1170.1, 25.1) | 759.0 (718.8, 16.9) |
| Quantity::to_unit (kW.h -> kWh) | 357.3 (346.5, 8.0) | 320.1 (306.1, 4.2) |

Fast path rows are unchanged within noise (scalar 0.61 vs 0.62 ns; `apply_slice` 10^6 0.554
vs 0.558; `apply_in_place` 10^6 0.824 vs 0.813). `apply_slice` 10^3 linear read 0.118 -> 0.131 ns
(+11 percent, MAD 0.002-0.004) although that code did not change; the same build measured
0.115 -> 0.131 in `bench-check`, which passes (under the 0.03 ns floor). It looks like a code
layout effect, not a real regression, but it was not proven. Not helped: `Ratio::checked_add`
(still does its gcd), `Quantity::to_unit` (dominated by prepare/allocation, not the exact apply).

## Regression guard status (2026-11-10)

`cargo xtask bench-check` compares a fresh `m0` run with `baseline-m0.tsv`. It is a manual local
check, not part of `cargo xtask ci` or any workflow. On 2026-11-10 it failed on a cloud VM with
slowdowns of 12 to 47 percent on the scalar and slice `apply` rows, with and without the ADR-013
change. What was measured, all on that one VM (Intel Xeon 2.10 GHz, 4 vCPU, rustc 1.99.1):

* **The baseline does not fit this machine and compiler.** It was recorded with rustc 1.97.0 on
  another VM. Across all 53 rows, the median row of a fresh run was 9.2 percent slower than the
  baseline, and rows that run no Dimvexa code were slower too (`plain multiply x * 3.6` +12.8,
  `slice memcpy ceiling 10^5` +17.2, `slice plain multiply loop 10^3` +21.0 percent). Two runs of
  the same build differ by a median of 4.0 percent per row, so noise alone does not explain 9.
* **The baseline predates the exact-path speed-up.** It was recorded on 2026-11-08 04:59 UTC; the
  commits that made `apply_exact_f64` about 8 times faster came at 08:06 UTC the same day. The
  baseline still holds the old exact rows (315.5 and 381.4 ns, now 43 and 55 ns), so those two
  guarded rows could not catch a regression of up to 7 times today.
* **The change under test is not the cause.** Interleaved on the same machine and compiler, the
  commit before ADR-013 (`3e59c3b`) against the one after (2 runs each, best median per row):
  median row +0.5 percent, 14 of 16 guarded rows within +-5 percent. Two rows differed at the
  branch tip: `single call via black_box(&conv)` +7 to +11 percent and `slice affine apply_slice
  10^3` +21 percent (0.200 to 0.246 ns per element).
* **Those two rows are code layout, not code.** The apply code did not change in any commit.
  Measured per commit (best median of 3 interleaved runs, ns per element) for `slice affine
  apply_slice 10^3`: `3e59c3b` 0.204, first ADR-013 commit 0.231, second 0.207, `f16edd5` (last
  code commit) 0.196, then `8fdaf7e` (only benchmark data changed) 0.200, and `9e077af` 0.233
  (+17 percent). The only change in `9e077af` is the version bump 0.2.2 to 0.3.0 (`crates/` is
  byte-identical to `f16edd5`), so the row moved with a version string. Same code, only the
  workspace version changed (4 builds, best of 3 runs): 0.2.2 gives 0.198, 0.3.0 gives 0.232,
  0.4.1 gives 0.197 and 0.2.3 gives 0.228 ns per element, while `slice linear apply_slice 10^3`
  goes the other way (0.149, 0.131, 0.146, 0.130 ns): a build identity, not the code, picks one of
  two modes about 14 percent apart. The same bimodal result appears with the version fixed and
  only `RUSTFLAGS="-C metadata=bench-layout-K"` changed (one run each, K = 0 to 4: 0.196, 0.225,
  0.223, 0.196, 0.223 ns). Why a metadata hash picks the mode (probably the link order of the
  functions in the bench binary) was not examined. The row goes up and down across commits with no
  trend, and `single call via black_box(&conv)` does the same (0.79 to 0.91 ns across the same
  builds, no consistent step). Both are 1000-element or one-call micro rows (0.04 ns per element
  is about 40 ns per call), where alignment of the loop decides the result. Lesson for the guard:
  a single row above the threshold after a build that changed nothing in the apply path is
  not proof of a regression; check it against a control build before acting.

`cargo xtask bench-check --against REV` (added the same day) does the A/B run above in one
command: it builds REV in a temporary worktree and alternates REV and the working tree on this
machine, up to 3 rounds, best median per row and build. If a guarded row is still slow, it
rebuilds both sides under other `-C metadata` salts (`--layouts`, default 5) and judges by the
best layout per side, so a layout mode cannot fail the check; a regression that is slow in every
layout still does (the output lists the per-layout values of such a row). The 0.03 ns jitter
floor can still hide a mode difference on the 10^3 rows (0.028 ns here). Run on `3e59c3b` against this branch it
reproduced the manual result: 14 of 16 guarded rows within +-3.3 percent, and the same two rows
flagged (`single call via black_box(&conv)` +11.4, `slice affine apply_slice 10^3` +21.2 percent),
which the per-commit run above attributes to the version bump.
On a shared cloud VM use it instead of the stored baseline, which is only valid on the machine
and compiler that recorded it (and must be re-recorded with `--update` before it is used again).
