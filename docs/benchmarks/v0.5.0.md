# Benchmarks for 0.5.0 (ADR-018 step 1: the number type with powers of ten and pi)

Date of the runs: 2026-11-11. This file records the speed gate of
[ADR-018](../adr/018-constants-and-exact-pi.md), step 1 (every number is
`num/den * 10^k * pi^m`; the angle units are exact; `eV` and `Da` are added). Only numbers measured
here are quoted; nothing is compared with another library.

## Machine and method

| | |
|---|---|
| Machine | shared cloud VM, 4 logical CPUs (Intel Xeon @ 2.10 GHz), 16 GB, Linux 6.18 x86-64 |
| Compiler | rustc 1.99.1 (58cf8f9c3 2026-10-13) |
| Profile | `bench` (release, thin LTO, codegen-units 1, debug 1) |
| Harness | `cargo bench -p dimvexa --bench m0` (std only, 15 samples per row, median per row) |
| Before | commit 1ca7d0d (the merge base with main, release 0.4.0), built in a separate worktree |
| After | the working tree of this change |

Two measurements, both with before and after run alternately on the same machine:

1. **The gate:** `cargo xtask bench-check --against 1ca7d0d` (up to 3 rounds per side, best median per
   row, 10 percent threshold, only the rows that exist in both trees).
2. **The new rows** (angle conversion, prepare, `eV`): the new `crates/dimvexa/benches/m0.rs` was copied
   into the before worktree (the `eV` rows are skipped there), and both sides ran 6 times alternately.
   The table shows the median of the 6 medians. A row marked "new row" has no before value.

Reading it:

* **Hot path unchanged.** `scalar linear apply, deg -> rad (throughput)`: 0.789 before, 0.737 after ns per call
  (the factor is an `f64`, however it was derived).
* **`apply_exact` (rational in, rational out) got faster for angles**: 175 -> 43 ns, because the
  old convergent of pi made the fractions large; `1/180 pi` multiplies small numbers.
* **`apply_exact_f64` for a factor with pi is about 15 times slower**: 47 -> 704 ns for `deg -> rad`. It is
  the price of a proven rounding: the exact result is no longer one `i128` division but two 128-bit
  directed-rounding quotients (`crates/dimvexa-core/src/approx.rs`). The rows for plain fractions
  (`apply_exact_f64 (linear ...)`, `(affine ...)`) do not change within noise. This is the exact path,
  not a hot-path row of the gate, but `apply_exact_f64 (deg -> rad ...)` carries the guarded prefix and will be
  guarded from the next stored baseline on. A faster version is possible (compute the lower and upper bound
  of the factor once at prepare and only multiply by the 53-bit mantissa of `x`); it was not done here.
* **Prepare costs more for a factor with pi**: `conversion("deg","rad")` 992 -> 1365 ns (+37.6 percent, about
  370 ns for the one-time 128-bit rounding). `eV -> J` prepares in 1196 ns (no baseline).
* **Parsing looks a few percent slower**: the median of the three cold-parse rows is +7, +12.5 and +15
  percent, but the individual runs overlap heavily (for example `kg.m2/s2` before 2330 to 3690, after 2430
  to 3610 ns), so the size of the effect is uncertain; it is not shown to be zero. A plausible cause is the
  size of `Ratio` (48 bytes instead of 32, because of the two exponents), which every `UnitExpr` copies;
  that cause was not tested. These are not hot-path rows and a unit is not parsed on the hot path.
* `Ratio::checked_mul` and `checked_add` are not slower (the apparent speed-up is noise).

## What was not run

* The criterion and iai suites in `extras/` and the cross-library comparison (`benchmarks/`): they need
  network and were not run; there is no comparison with another library here.
* The Python and WASM bindings and the Excel add-in were not benchmarked. I did not build them. A review agent
  reported building the Python wheel and passing its 15 tests, and that the WASM crate compiles; I did not
  re-run that myself.
* No other machine, compiler or profile, and no `--layouts` run.
* The stored baseline `docs/benchmarks/baseline-m0.tsv` was re-recorded for 0.5.0 on this machine and compiler
  (`cargo xtask bench-check --update`, median of 3 runs, 59 rows including the new angle and `eV` rows and the renamed
  `registry construction, all table units (cold start)` row, 161 us for 106 units). It is only comparable on this machine.
* Correctness checks that go with the speed claim were run: `differential.rs` (1 ulp linear, 2 ulp
  affine, bounds unchanged), `exact_f64.rs` (including 360 values from an independent oracle for the
  angle, `eV` and `Da` conversions), `overflow_census.rs`, `zero_alloc.rs` and the property tests, all via
  `cargo xtask ci` (exit status 0).

## Re-check after the review fixes

A review found two CLI bugs (`--json` failing for a power of ten that does not fold, and an overflow
for `2e29 eV` that fits), fixed in `Ratio::checked_mul` (a retry that moves factors of 10 into the
exponent, only beside an operand that already has a ten exponent) and in the CLI. The hot-path
rows do not call `checked_mul`, but the gate was run again:

* Run 1 (`bench-check --against 1ca7d0d`) failed on 4 rows (+22.9 percent `apply_exact_f64 (affine)`,
  +11.7, +35.2, +14.4 percent on micro rows). Run 2 failed on 3 **different** rows (`single call`
  +16.3, `slice affine apply_slice 10^6` +11.7, `slice linear apply_slice 10^3` +39.3 percent) while
  others improved by up to 26 percent. The set of flagged rows changes from run to run.
* `bench-check --layouts 5` (the check the tool recommends for micro rows) ended with
  `bench-check: ok` after 2 layouts. The tool warns that a real slowdown smaller than the layout
  spread (about 10 percent here, for example `scalar linear apply (latency chain)` 3.764 vs 4.154)
  can pass this way, so this is a no-regression result within the noise of this VM, not proof
  that there is no small slowdown.

## What was measured, exactly

The "after" numbers are the working tree at the time of each run: sections 1 and 2 before the review fixes
(commit `f73ceea` plus the benchmark rows), the re-check at `d8c5f81`. The final code of 0.5.0 also contains
`1004dde` (the affine refusal in `Conversion::new`, a prepare-time check) and was not measured as a whole;
the hot-path rows do not call it. The raw output of the re-check runs is not stored in the repository.
